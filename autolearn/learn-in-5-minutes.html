Introduction to Kubernetes (K8s)

Docker made it easy to package an application together with everything it needs into a container that runs the same way on any machine. For a handful of containers, running them by hand works fine. But once teams were running hundreds or thousands of containers across many servers, a new set of problems showed up:

  • Scalability. Adding and removing containers by hand as traffic rises and falls is slow and error-prone.
  • Multi-cloud. Running the same application across different cloud providers, or a mix of cloud and on-premise servers, means managing each environment separately.
  • Security and resource management. Every container needs the right access controls and the right share of CPU and memory, and keeping track of that across a fleet is hard.
  • Rolling updates and zero downtime. Shipping a new version without taking the application offline requires carefully replacing containers a few at a time.

Container orchestration tools were created to solve these problems, and Kubernetes has become the most widely used of them.

Kubernetes

Kubernetes is an open-source container orchestration platform that automates the deployment, scaling and management of containerized applications. It was designed at Google, building on more than a decade of experience running production workloads on internal systems called Borg and Omega, and was released as open source in 2014. In 2015 Google donated it to the Cloud Native Computing Foundation (CNCF), which maintains it today. The name comes from the Greek word for helmsman or pilot, and it is often shortened to K8s, since there are eight letters between the K and the s.

A helpful way to picture Kubernetes is as the conductor of an orchestra. Each container is a musician, and the configuration you write describing how your application should run is the sheet music. The conductor doesn't play an instrument, but it makes sure every musician comes in at the right time and plays the right part, so the whole piece sounds right.

Key features of Kubernetes

  • Automated scheduling. Kubernetes decides which machine each container should run on, based on the resources it needs and what each machine has free.
  • Self-healing. Containers that crash are restarted, containers on a failed machine are rescheduled elsewhere, and containers that fail their health checks are replaced.
  • Rollouts and rollbacks. New versions are rolled out gradually, and if something goes wrong the change can be rolled back to the previous version.
  • Scaling and load balancing. The number of running copies can be scaled up or down, manually or automatically, and incoming traffic is spread across the healthy copies.
  • Resource optimization. By packing containers efficiently onto machines, Kubernetes makes better use of the hardware you pay for.

Monolithic vs microservices

Traditionally, applications were built as a monolith: one large codebase in which every feature, from user accounts to payments to search, is built, deployed and scaled together. A bug in one part can take down the whole application, and scaling one busy feature means scaling everything.

A microservices architecture splits the application into small, independent services, each responsible for one feature and each running in its own container. Teams can update and scale each service on its own. The trade-off is that an application may now consist of dozens or hundreds of containers that all need to be deployed, connected, monitored and kept healthy. Managing that complexity is exactly the job Kubernetes was built for.

Terminologies in K8s

  1. Pod. The smallest deployable unit in Kubernetes. A Pod wraps one or more containers that share storage and a network address. Pods are temporary: when one fails, it is replaced rather than repaired.
  2. Node. A physical or virtual machine that runs your Pods. Each node runs a container runtime, the kubelet and kube-proxy.
  3. Cluster. A group of nodes working together. A cluster has a control plane (sometimes called the master) that makes decisions and stores the desired state, and worker nodes that run the application.
  4. Deployment. An object that describes the desired state of an application, such as which container image to run and how many replicas. It is declarative: you describe the result you want, and Kubernetes works out how to reach it.
  5. ReplicaSet. Ensures that a specified number of identical Pods is running at all times. Deployments create and manage ReplicaSets for you.
  6. Service. Gives a set of Pods a single, stable network address and spreads traffic across them, so other applications can reach them even as individual Pods come and go.
  7. Ingress. Manages access from outside the cluster, routing HTTP and HTTPS requests to the right Service based on rules such as the host name or path. It acts as a reverse proxy in front of your Services.
  8. ConfigMap. Stores non-sensitive configuration data, such as settings and environment variables, separately from the application code, so the same image can run with different configurations.
  9. Secret. Stores sensitive information such as passwords, tokens and keys, kept separate from ordinary configuration and given only to the Pods that need it.
  10. Persistent Volume. Storage whose lifetime is independent of any individual Pod, so data survives when Pods are restarted or replaced.
  11. Kubelet. An agent that runs on every node. It receives instructions from the control plane, makes sure the Pods assigned to its node are running and healthy, and reports their status back.
  12. Kube-proxy. A network component on every node. It maintains the networking rules that let Pods talk to each other and route traffic sent to a Service to the right Pod.

Conclusion

Kubernetes turned running containers at scale from a manual, fragile process into an automated one. You describe the state you want, and Kubernetes schedules, heals, scales and updates your containers to keep it that way, across any number of machines and any cloud. Understanding its core building blocks (Pods, nodes, clusters, Deployments, Services and the rest) is the first step to running modern applications with it.
